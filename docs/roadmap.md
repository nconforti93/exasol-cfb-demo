| D24 | 2026-10-21 | **Advertise more predicates than are pushed** (`<>`, `LIKE`, `OR`, `NOT`, `IS NULL` …): translate only `=`/`IN`/ranges/`AND`/same-parameter `OR` on `P_` columns, reject every other parameter predicate with a message, re-apply all other filters as a residual; no aggregate, projection, `LIMIT` or join pushdown | Unadvertised predicates on `P_` columns would be evaluated by Exasol against NULL echo values and return silently empty results. | D25 | 2026-10-21 | **The call budget counts planned requests per virtual-table access**, stored slices included (`MAX_CALLS_PER_QUERY`, default 10); stored-only queries (`REQ_SOURCE = 'STORED'`) are exempt | The adapter can't see the load log; a plan-time ceiling is safe and visible in `EXPLAIN VIRTUAL` |
| D26 | 2026-10-21 | **Read-through by exact slice key:** a slice (`TABLE_NAME`, canonical request path) is served from `CFB_CORE` iff `CFB_META.LOAD_LOG` holds a final row for it; mirrors have the virtual table's columns | Simple, provable, exactly once per slice; verified live in S2 (stored slice 0 calls, missing slice exactly 1). | D27 | 2026-10-21 | **Fetch log:** every table carries `REQ_*` request columns and the pushdown SQL starts with a JSON manifest of the planned requests; consumers persist `CFB_META.FETCH_LOG` (`vs/host/fetchlog.py`) | UDFs cannot write tables; actuals travel with the rows, the plan with `EXPLAIN`, zero-row requests stay visible |
| D28 | 2026-10-21 | **Child tables** for arrays of objects: 1-based position columns, reviewed parent keys, hoisting only where declared, a curated subset plus `RAW_JSON` for objects over 500 fields | A positional join always works; heuristic keys would fail silently |
| D29 | 2026-10-21 | **Integration tests make zero CFBD calls:** `TEST_` namespace, mock CFBD API addressed by IP with a marker key, synthetic recordings; a guard refuses `CFBD_API` | CFBD terms (the repo goes public), quota, and no risk to stored data or the real key |
| D30 | 2026-10-21 | **No reliance on hidden defaults:** the overrides turn each one into an explicit sent-and-echoed default, a requirement, or a verified "omission means all" (S1); `/plays/stats` requires `gameId` (2,000-row cap); a prose lint fails generation on uncovered rule-like descriptions | Implements D14 mechanically and keeps it from drifting on spec bumps |
| D31 | 2026-10-21 | **Fan-out runs as one SET group with a bounded thread pool** (`MAX_PARALLEL_FETCHES`, default 6) | Speed doesn't depend on DB load and CFBD concurrency stays under control; S2: 6 slices fetched concurrently in 424 ms against 2.3 s sequentially. Chosen by Nico |
| D32 | 2026-10-21 | **`sys` owns the real deployment;** readers get the role `CFB_READER` with `SELECT` on `CFBD_VS`; the `TEST_` namespace keeps a dedicated owner, so the script-bound grant model stays tested | On a Personal DB a separate owner adds a password and a step without demo value. | D33 | 2026-10-22 | **Loader entry points are Lua scripting programs** (`CFB_INFRA.BACKFILL`, `CFB_INFRA.REFRESH_WEEK`, run with `EXECUTE SCRIPT`); host Python only deploys, wraps (estimate, `CONFIRM`, ledger) and runs snapshot/restore | Lua is the only way to run multi-statement SQL inside Exasol (Python UDFs cannot write tables, the adapter cannot run SQL). | D34 | 2026-10-22 | **The demo line is `EXECUTE SCRIPT CFB_INFRA.REFRESH_WEEK(2026, N, 'regular')`, which returns the step timeline** (step, status, seconds, slices, rows, calls), never `WITH OUTPUT` | Exasol has no `CALL` statement (`CALL` is only a reserved word). | D35 | 2026-10-22 | **Set logic lives in SQL views; the Lua stays thin, runs every statement through `pquery` and every entry function through `pcall`; the views are tested before the Lua** | Finality, gaps, gating, queue order, quarantine, orphans and the quota arithmetic are declarative, inspectable (`SELECT * FROM CFB_META.BACKFILL_QUEUE` is the estimate) and testable on the engine early. `query()` ends the script on an error, so rollback, log and lock release could not run; a script that ends in an error commits its open transaction under autocommit (probe 1.1b) |
| D36 | 2026-10-22 | **Read-through stays on during loads:** batch queries read `CFBD_VS` and keep only fetched rows (`REQ_SOURCE <> 'STORED'`); the loader never issues `ALTER VIRTUAL SCHEMA`. | D37 | 2026-10-22 | **Stage, then swap, in one transaction per batch of one plan entry** (`ENTRY_ID`, at most `MIN(MAX_CALLS_PER_QUERY, allowance)` slices): fan-out into `CFB_STAGE.<T>`, then `DELETE`+`INSERT` into `CFB_CORE`, `MERGE` into `LOAD_LOG`, `FETCH_LOG` rows, stage cleared, `COMMIT` | One `WHERE` clause expresses a batch (two entries of one table cannot share one). The HTTP time stays outside `CFB_CORE`'s write window, a failed batch leaves no trace, earlier batches stay committed (resumable), and other sessions never see a half-replaced slice |
| D38 | 2026-10-22 | **Slice keys come from templates compiled by the adapter's own planner** (sentinel values at deploy); each batch is checked with a zero-call `EXPLAIN VIRTUAL` manifest comparison before any request | The slice-key grammar exists once, so planned and requested keys cannot drift; a drift costs nothing to detect. | D39 | 2026-10-22 | **One reviewed load plan, `loader/load-plan.yaml`,** compiled into `CFB_META` at deploy: per entry table, slicing (`none`/`season`/`season_range`), seasons, gaps, fixed params, refresh class, profile, priority; several entries per table allowed; invalid plans change nothing and list every problem | One reviewed file decides what costs calls, and the validator uses the adapter's rules, so an entry the API cannot serve fails at deploy, not on a paid call. | D40 | 2026-10-22 | **Refresh classes `static` and `weekly` with date-based finality** (`season_rollover` 08-01, `season_final_after` 02-15 of the next year); D15's storage classes are derived from the plan, not configured. `season_week` slicing, an `archive` class and the `full` entries are backlog | Historic seasons contain cancelled games that never complete, so "all games completed" is not a rule; dates are deterministic and testable with a clock seam. | D41 | 2026-10-22 | **The weekly refresh re-fetches the current season's season slices** (with delete+insert) instead of adding week slices; `week` and `season_type` are validated against the stored calendar, name the run and feed the registered steps | Read-through matches slice keys exactly (D26), so week slices next to a season slice would store every game twice. | D42 | 2026-10-22 | **Budget in `LOADER_CONFIG` (plan file, `LOADER_CONFIG=` override per deploy), checked against `/info`, two guards.** `CFB_META.QUOTA`: `PROJECT_BUDGET = LEAST(MONTHLY_LIMIT, budget)` caps the key's whole monthly use; `REFRESH_SPENDABLE`, `BACKFILL_SPENDABLE = REFRESH_SPENDABLE - reserve`. | D45 | 2026-10-22 | **Snapshots: gzip CSV written and read by pyexasol (not Parquet via exapump), scope `CFB_CORE` + `LOAD_LOG` + `FETCH_LOG`,** in `~/.cfb-demo/snapshots/<name>/` (outside the repo and OneDrive, no S3); a manifest with catalog and plan hashes and per-column fingerprints; an atomic restore through a landing schema, refused on a column or catalog-hash difference unless `FORCE=yes` (columns always); zero API calls; also the rehearsal reset. **Exception:** a `DOUBLE` with more than 15 significant digits comes back rounded to its text form (relative change at most 4e-12) | Probe 1.2: exapump 0.13 fails on VARCHARs with a comma, quote or newline (every JSON column), trims spaces and writes untyped Parquet; pyexasol round-trips every type exactly except full-precision DOUBLEs. ## Demo flow (~25 min)
1. **Hook (2):** the app as of Sunday before week N+1's refresh. "Your team, its playoff odds."
2. **The API is a schema (5):** `CREATE VIRTUAL SCHEMA` over CFBD; `SELECT` from an endpoint; inspector shows the HTTP; a year range fans out in parallel; a contradiction costs 0 calls; 157 years of games already persisted.
3. **One call refreshes everything (5):** `EXECUTE SCRIPT CFB_INFRA.REFRESH_WEEK(2026, N, 'regular')` (Exasol has no `CALL`, D34); the timeline shows fetch → merge → model → predictions → 100k sims with seconds and calls per step; then the sim count as the dial (laptop 100k, AWS 1M).
4. **Pages move (8):** scorecard ("model went 41–9"), upset of the week ranked all-time, playoff odds with arrows, what-if toggles + rooting guide on a bubble team, head-to-head with a live preview fetched on click.
5. **AI (4):** the chat sets a what-if, explains a swing, answers a question outside the pages; shows its SQL.
6. **Close (1):** one platform, any analysis; repo link.
