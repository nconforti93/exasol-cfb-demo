# exasol-cfb-demo — Project Rules

A college football analytics platform on Exasol: an OpenAPI-generated Virtual Schema over the whole CFBD API, with all history persisted and a weekly `REFRESH_WEEK` call. The app's v1 pages are playoff odds (Monte Carlo, Python SET UDFs), predictions + scorecard, upsets and head-to-head, plus an MCP chat. Decisions D1–D49 are in `docs/roadmap.md`. Product intent and scope are in `specs/mission.md`, architecture in `specs/architecture.md`, phase plan in `docs/roadmap.md`.

## Spec-driven development (speq)

- Every feature goes through `/speq:plan` → `/speq:implement` → `/speq:record`. Each roadmap phase is one plan.
- `specs/` defines only user-visible behavior. Domains: `cfbd-vs/`, `loader/` and `model/` (recorded); planned: `sim-engine/`, `api/`, `app/`, `chat/`. The serving code lives in `analyses/`.
- Layering rules: `CFB_API` reads `CFB_MODEL` and `CFB_SIM`; apps and the MCP user read stored views through `CFB_API`. `CFB_API_LIVE.QUOTA` is app-only. A paid game preview uses Phase 6's guarded operator path with a literal `P_GAME_ID`, because Exasol does not push the required filter through a serving view.
- Endpoint classes (D15): `stored` (demo scans it broadly; in `CFB_CORE`), `federated` (selective on-demand queries via the VS; read-through serves stored slices at 0 calls; `PROMOTE()` is deferred to the backlog), `unavailable` (tier-gated). Never route a broad scan through the API: if a page or analysis needs to scan a federated endpoint, reclassify it as stored.
- Testing tiers, toolchain/build, CI, deployment and licensing are NOT specs. They live here as dense bullets.
- The engine contract (inputs, RNG, outputs) is a spec in `sim-engine/`. One engine: Python (numpy, vectorized across sims), D16.

## Data and secrets

- The CFBD API key lives ONLY in the Exasol CONNECTION `CFBD_API`, created by the user with plain SQL (D18, see `docs/user-guide.md`); there is no key tool and Claude never handles the key. Only `CFB_INFRA.CFBD_FETCH` may read it: readers (`CFB_READER`, app, MCP) reach the key only through the virtual schema. On the real deployment `sys` owns everything ([20]; there is no `CFB_OWNER`), so `sys` can read every connection and needs no grant; the `TEST_` namespace keeps its own owner with the script-bound `GRANT ACCESS ON CONNECTION … FOR SCRIPT CFB_INFRA.CFBD_FETCH`. The backend never calls CFBD. The key never goes in .env, SQL files, VS properties, logs, fixtures or frontend code.
- **Deploy → grants rule (amended by [20]):** order is `make deploy` → create `CFBD_API` with plain SQL (`docs/user-guide.md`) → `make deploy` again (syncs `API_FEATURES` from the free `/info`) → `make grants`. Grants creates `CFB_READER` on `CFBD_VS`, `CFB_APP` on `CFB_API` and `CFB_API_LIVE`, and `CFB_MCP` on `CFB_API` only. `CREATE OR REPLACE` of `CFBD_FETCH` drops a script-bound grant even for identical text (verified 2026.2, probe 1.4o), so deploy replaces the UDF only when its body changed. That matters only for a prefixed namespace with its own owner (`TEST_`): re-run `make grants ARGS="--prefix TEST_"` after a deploy that replaced it. The real deployment needs no connection grant.
- **Secrets never in the repo or OneDrive; use `~/.cfb-demo/app.env`** (mode 0600; `make app-env` creates it; `CFB_APP_ENV` overrides the path; D44). Passwords and API keys are read from the environment, then that file, through `vs/host/appenv.py`. A `*_PASSWORD` or `*_API_KEY` key in the repo `.env` stops the app. Never print or log a value.
- Never grant `ACCESS ANY CONNECTION`, or `ACCESS` on `CFBD_API` to any other script, user or role.
- CFBD terms forbid redistributing raw data, and the repo goes public on exasol-labs. Never commit raw API responses, dumps or replay fixtures. Recorded responses stay in local `cache/` (gitignored) and in BucketFS. Unit-test fixtures are small and synthetic.
- Quota: CFBD free tier, 1k calls/month (shared with CBBD); tier 2 is the fallback. Never re-backfill a rebuilt DB: `make restore` from the private snapshot (gzip CSV, D11, D45). Snapshots live outside the repo and outside OneDrive. The per-query call budget still applies. Integration tests make zero CFBD calls. Live calls only from `make backfill` / `make refresh` (which print a call estimate first and need `CONFIRM=yes`), the guarded app preview operator path and the recorder. Pinned API spec: `vs/openapi/cfbd-openapi-5.33.0.json`.
- **Live ledger:** every live CFBD call is appended to `cache/live-calls.jsonl` (gitignored; in a git worktree it is the **main** working tree's file, so there is one ledger; `LEDGER_PATH` overrides), and a plan's calls are capped by the ledger total, a hard cap that a recorded call cannot exceed. Caps are in `vs/live/ledger.yaml` (`plans`: per plan over all months; `months`: the owner's authorization per UTC month across plans, enforced against `/info` used calls + estimate; a month without an entry refuses live calls). The owner edits that file, never Claude. `/info` is free and does not count. Never write live calls any other way. `make backfill` / `refresh` record one entry per run (`<KIND>#<run id>`, the larger of the script's measured calls and the `/info` delta), also after Ctrl-C or a timeout (new session, `KILL SESSION` of a still-running script, worst case when nothing is readable; [47]), use the ledger unless the virtual schema reads `CFBD_API_MOCK` ([49]), and cap `MAX_CALLS` at the ledger room; `LEDGER=off` disables the ledger for people with their own key and is for them only.
- **Two budget guards (D42):** the in-database one is `CFB_META.QUOTA` (`PROJECT_BUDGET = LEAST(MONTHLY_LIMIT, monthly_call_budget)` against `/info` used calls, so it caps every SQL client; `BACKFILL_SPENDABLE = REFRESH_SPENDABLE - refresh_reserve`; a refresh may use the reserve), the second is the ledger. Per-target overrides live in `vs/live/loader-config.yaml` and every `make deploy TARGET=<t>` applies them (`aws`: `monthly_call_budget: ledger` = the ledger's cap for the deploy's UTC month, `refresh_reserve: 50`; decision [46]), so a plain redeploy never lifts the AWS budget; `LOADER_CONFIG="k=v,..."` wins per setting and is printed. Redeploy once after a month change to follow the new cap.

## Testing and toolchain

- **Toolchain:** Python 3.12 only, managed with uv (`uv.lock`, `package = false`; dev group pytest, pytest-cov, ruff, mypy, PyYAML, pyexasol). Every `make` target runs through `uv run` (except `db-check`, plain `python3`). `vs/cfbd_vs` is stdlib-only because it is embedded in the adapter and fetch UDF scripts; `vs/gen`, `vs/host` and `loader/*.py` run on the host (`loader/lua/*.lua` runs in the database). Ruff line length 100.
- **Make targets:** `generate` (catalog + mirror DDL from the pinned spec and `vs/catalog-overrides.yaml`), `bundle` (adapter and fetch UDF script bodies into `build/sql/`; fails from 1,990,000 characters, Exasol's script cap is 2,000,000), `test` (unit + cli, no DB), `test-it`, `test-network`, `lint` (`ruff check`, `ruff format --check`, `mypy` strict over `vs`, `loader`, `model`, `engine`, `analyses`, `scripts`, `tests`), `coverage`, `deploy`, `grants`, `dns-check`, `record`, `backfill`, `refresh`, `quota`, `snapshot`, `restore`, `snapshots`, `model`, `sim`, `api`, `api-docs`, `db-check`. Targets that need a database run `db-check` first. Details in `specs/mission.md` § Commands.
- **`TARGET=local|aws`** applies to every DB target (`make deploy TARGET=aws`, also `backfill`, `refresh`, `quota`, `snapshot`, `restore`); the loader reuses `vs/host/target.py` and has no second target module (D46). `make test-it` is `local` only: it needs the DB container's network namespace for the mock sidecar. `ARGS` passes options through (`make deploy ARGS="--property MAX_CALLS_PER_QUERY=5"`; `--prefix` deploys a namespace as sys and is refused with the real connection).
- **Coverage:** `make coverage` runs unit + cli only and must reach at least 90 % line coverage for `vs/cfbd_vs`, `vs/gen` and `loader` each (`fail_under` in `pyproject.toml`, one report per package). `make lint` must be clean (mypy strict).
- **Test tiers:** `tests/unit` (pure functions, no DB, no network), `tests/cli` (generator and script entry points), `tests/it` (marker `it`, against Exasol Personal local). Unit fixtures are small and synthetic (`tests/synthetic/fake.py` generates schema-valid responses); no raw CFBD data in tests.
- **Mock sidecar + replay:** live mode in `tests/it` talks to a mock CFBD server (`tests/mock_cfbd/`) running as a sidecar container in the DB container's network namespace (`CFBD_API_MOCK` = `http://127.0.0.1:<port>`, marker key, not reachable from the host). It must be restarted after `exasol stop/start -d local` (the harness does this itself). Replay is tested with synthetic recordings in BucketFS. UDFs cannot reach the host: rootless podman uses `--disable-host-loopback`.
- **`TEST_` namespace:** the harness deploys `TEST_CFB_*` / `TEST_CFBD_VS` with a generated owner `CFB_TEST_OWNER` and reader `CFB_TEST_READER` (random passwords, process memory only) and drops it all at the end (and clears leftovers of a crashed run at the start). `tests/it` must never reference the real `CFBD_API` connection: collection fails, and the session start refuses a test schema that reads it. **Zero CFBD calls** in `make test-it`.
- **Shared IT lock:** the `TEST_` namespace and the mock are single-session. Several sessions or agents that share the local DB must serialize integration runs with one lock file: `flock <scratchpad>/cfb-it.lock make test-it` (create the file with any `flock` if /tmp was wiped). Never run two at once, and never run them while a benchmark has the DB.
- **`make test-network`:** only the `network`-marked test (DoH end to end from the UDF sandbox plus a TLS handshake with `api.collegefootballdata.com`, no HTTP request, 0 CFBD calls). Needs HTTPS egress and never skips; it is excluded from `make test-it`. `make dns-check` is the same check as a live gate.

## Loader (Phase 2, `loader/`)

- **`make deploy` after every edit of `loader/load-plan.yaml`** (it validates against the catalog, compiles slice templates and rewrites the plan tables, views and Lua scripts; an invalid plan changes nothing). `uv run python -m loader.plan --check --estimate` prints the call estimate at 0 calls (demo: 217; weekly refresh: 4). Never reorder entries without a redeploy: the position is `ENTRY_ID`.
- **Entry points are Lua** (`CFB_INFRA.BACKFILL(run_profile, from_season, max_calls)`, `CFB_INFRA.REFRESH_WEEK(season, week, season_type)`, `RUN_LOCK`), not Python. The demo line is `EXECUTE SCRIPT CFB_INFRA.REFRESH_WEEK(2026, N, 'regular')`: Exasol has no `CALL`, the argument count must match exactly, and **never `WITH OUTPUT`** (it discards the result table).
- **Lua rules** (`loader/lua/*.lua`, bundled by `loader/bundle.py`): every statement through `pquery`, every entry function through `pcall`, no bare `query(`; the error path is `ROLLBACK`, log, `COMMIT`, then `error(msg, 0)` (a script that ends in an error commits its open transaction under autocommit); Strings written to `exit()` or a VARCHAR column are cut at a character boundary first (right truncation or a cut UTF-8 sequence fails the whole script), and result column names must not be reserved words (`LOG`, `RESULT`, `SCOPE_USER` failed). The bundler double-quotes every identifier; `::name` inserts text verbatim and is for deploy-time constants only, every value is bound as `:name`. Lua scripts run with the **caller's rights** (`sys` on the real deployment); an app-triggered refresh needs a loader role (Phase 6).
- **The loader never switches `READ_THROUGH` and never issues `ALTER VIRTUAL SCHEMA`** (properties are global; a unit test scans the sources). Batch queries keep `REQ_SOURCE <> 'STORED'`. **Pages, the chat and analyses read current-season data from `CFB_CORE`, never through `CFBD_VS`:** current-season slices are never final, so a VS query on them is a live call.
- **Time:** one UTC expression (`CONVERT_TZ(CURRENT_TIMESTAMP, SESSIONTIMEZONE, 'UTC')`) for every loader timestamp; Personal's session time zone is `CET`. Not `SYSTIMESTAMP`, not `POSIX_TIME`.
- **Run lock:** a `RUNNING` row in `CFB_META.LOAD_RUN`. Script kinds (`BACKFILL`, `REFRESH_WEEK`, Phase 4's `SIMULATE`) are stale when the session is gone, own or idle; host kinds (`SNAPSHOT`, `RESTORE`, `DEPLOY`) only when the session is gone or own. Host processes take it with `loader.runlock.run_lock` (autocommit off is refused, no nesting, work in the same session; `RUN_LOCK` refuses script kinds). Only the holder's session releases a row; a run whose row another session abandoned fails at its end. `make deploy` holds `DEPLOY` once the namespace has `RUN_LOCK` (the first deploy installs it). A registered refresh step must declare exactly `(run_id, season, week, season_type)` and must **not** take the lock (it would abandon the refresh's own row).
- **Failures and orphans:** a failed multi-slice batch is retried slice by slice; slices failing alone are quarantined after `quarantine_after` runs (clear with `DELETE FROM CFB_META.LOAD_FAILURES`); a backfill stops `FAILED` only after 2 consecutive failed batches ([45]); live batches are sized for 4 attempts per request, so a run overshoots `max_calls` by at most 3 calls ([48]); orphan slices (stored under a key the plan no longer plans) block the table until the owner migrates or deletes them. To re-fetch a stored slice set `LOAD_LOG.IS_FINAL = FALSE` and run backfill.
- **Snapshots** hold CFBD data: `~/.cfb-demo/snapshots/<name>/` (`CFB_SNAPSHOT_DIR` overrides), refused inside the repo or a OneDrive path, never committed or shared (`git ls-files '*.csv.gz' '*.parquet'` stays empty), no S3. Format gzip CSV via pyexasol (exapump's Parquet fails on commas, quotes and newlines in VARCHARs; `loader/exapump.py` is gone). Scope `CFB_CORE` + `LOAD_LOG` + `FETCH_LOG`; run logs stay per deployment. `make restore` needs `CONFIRM=yes`, refuses a column difference always and a catalog-hash difference unless `FORCE=yes`, and never reads `CFBD_VS` (0 calls). **DOUBLE exception:** a value with more than 15 significant digits comes back rounded to its text form (relative change at most 4e-12); the fingerprint sums the text form on both sides.
- **Loader test tier:** `tests/unit/test_loader*.py` (plan, templates, SQL, bundle, deploy) and `test_loadlib_lua.py` (the real `loadlib.lua` in embedded Lua 5.4 through `lupa`, `pquery` stubbed: statement order on the failure and lock paths), `test_backfill_lua.py` (the whole `BACKFILL` over a simulated queue, quota and failures: stop rule, batch sizing, measured spend), `test_target_config.py` and `test_loader_sources.py` (no `ALTER VIRTUAL SCHEMA` in the Python loader); `lupa` is imported directly, never skipped; `tests/cli/test_loader_cli.py`, `test_snapshot_cli.py`, `test_load_plan_cli.py` (fakes, no DB); `tests/it/test_*loader*`/`backfill`/`refresh_week`/`quota`/`load_plan`/`run_logs`/`run_lock`/`snapshot_restore` against Personal local in the `TEST_` namespace with small plan variants (`tests/it/fixtures/load-plan.*.yaml`, module-scoped deploys) and the mock API's counting `/info`. The harness reset truncates data tables only (`CFB_STAGE`, `LOAD_FAILURES` included) and keeps the deployed plan and config tables. **`LOADER_CONFIG.NOW_OVERRIDE` (the test clock) exists in the `TEST_` namespace only**; deploy removes it everywhere else. The harness grants the test owner `EXPORT`/`IMPORT` (pyexasol's file transfer needs them; `sys` has them).

## Model (Phase 3, `sql/model/`)

- **Stored data only, zero calls:** the model reads `CFB_CORE` and `CFB_META.{LOAD_PLAN, LOAD_PLAN_GAPS, LOAD_SLICES}`, never `CFBD_VS` (the lint and a dependency test enforce it). Analyses read only `CFB_MODEL`. One SQL file per object, deployed in one transaction by `vs/host/sqlobjects.py` (`make model`, also part of `make deploy`; `make model-check SEASON= WEEK=`, `make model-refresh`, `make model-docs` regenerates `docs/model-dictionary.md`, `make model-perf ARGS="--prefix PERF_"`). Lint: every object and column has a comment, the object comment starts "One row per ...", DDL names are unquoted upper case and not reserved, query bodies quote identifiers.
- **Derived tables and their rebuild rule:** `GAME`, `SEASON_WEEK`, `TEAM`, `RATING_SP`, `RANKING`, `TEAM_MEMBERSHIP`, `TEAM_SEASON`, `AS_OF_POINT` are tables (an `INSERT ... SELECT` of the former view query), current as of the last rebuild. `CFB_INFRA.REFRESH_MODEL` rebuilds them: refresh step 100 `MODEL` (registered by `make deploy`), post-hook of `make backfill` / `make restore`, `make model` / `make deploy`, `make model-refresh`. After `EXECUTE SCRIPT CFB_INFRA.BACKFILL` run directly, a manual edit of `CFB_CORE`, or an integration test that edits stored rows, run `make model-refresh` (tests: `harness.rebuild_model()`). Everything else is a view.
- **As-of rule:** points are `(AS_OF_SEASON, AS_OF_WEEK_SEQ)` (0 preseason, n regular, 100 + n postseason); one horizon, "known before the next week's first kickoff"; events visible when they happen, overwritten values (current SP+, lines, polls) from their fetch time; games whose teams depend on results are hidden until known. **Filter the as-of views with literal points** (read `CURRENT_AS_OF` first); a join to `CURRENT_AS_OF` evaluates every point (21 s). Read `GAME` at most once per query: Exasol evaluates a view referenced twice once, without the season filter.
- **Types:** venues are `GEOMETRY(4326)` (no `GEOGRAPHY` in Exasol) with `GREAT_CIRCLE_KM`; engine-facing values are `DECIMAL` (spreads (6,2), win probabilities (5,4), SP+ (6,2)).
- **`MODEL_CHECKS`:** ERROR checks stop the refresh chain in step 100; warnings are logged to `CFB_META.MODEL_CHECK_LOG` (for 2026 on the stored data: `CONF_CHAMPIONSHIP_MISSING`, `WEEK_ORDER_MISMATCH`, `ELO` coverage `PARTIAL`; see `docs/model-verification.md`).
- **Model tests:** `tests/it/test_model_*_it.py` on the synthetic league (`tests/synthetic/league.py`, scaled variant for performance), in the `TEST_` namespace; the model deploy itself takes the `DEPLOY` lock.

## Serving API (Phase 5, `analyses/`, `sql/api/`)

- `make api TARGET=local|aws` lints and deploys `CFB_API` and `CFB_API_LIVE` under the DEPLOY lock. `make deploy` installs the serving views after the model and simulation. `make api-docs` regenerates `docs/api-dictionary.md` from SQL comments without a database. Every view and column has a comment; view comments begin with the row grain. The deploy compiles each view and reads the comments back.
- `CFB_API` is a thin, stored-data serving layer over `CFB_MODEL` and `CFB_SIM`. It has no own data table or refresh step. Point-grain views carry `AS_OF_SEASON` and `AS_OF_WEEK_SEQ`; consumers read `CURRENT_POINT` first and filter with those values as literals. The app and MCP user have SELECT only through their respective serving roles. The chat role has no `CFB_API_LIVE` grant.
- The 33 stored views include `PLAYOFF_ODDS`, run and what-if sources, the precomputed `ROOTING_GUIDE`, frozen `PREDICTIONS` and scorecards, `MATCHUP_NEXT` with FROZEN/CURRENT prediction kinds, and `UPSETS` from stored lines or fitted Elo ranked all-time since 1978. `analyses/whatif.py` validates at most 16 distinct game outcomes, maps `GAME_ID` to the current run's `PATH_POS`, and reuses the engine's what-if SQL against serving views. `GAME_WIN_PROB` picks a stored line where available, else fitted Elo; it is stored-data SQL and makes no CFBD request.
- `CFB_API_LIVE.QUOTA` reads the free `/info` endpoint only when selected. Do not add a `GAME_PREVIEW` view: a local mock query proved Exasol does not push its required `P_GAME_ID` through a view. The Phase 6 operator sends a guarded direct query with a validated literal game ID. See `docs/api-verification.md` for the zero-call deployments and stored-query timings.

## Environment

- The repo path contains spaces (OneDrive). Quote paths, and pass `CURDIR` explicitly to make if a target breaks (adbc-vs-rs lesson).
- The docker-db container `cfb-exa` (127.0.0.1:9571) was only used for the S0 privilege spike; it is retired (D17).
- Runtime (D17): Exasol Personal 2026.2, local deployment `local` (nano, podman, 127.0.0.1:8563) plus the AWS `default` 3-node instance, selected with `TARGET=local|aws` (default `local`; `vs/host/target.py`). The sys password is read at run time from `~/.exasol/personal/deployments/<local|default>/secrets.json` (`dbPassword`) and never copied into files, env or logs; the starter-kit credentials file is obsolete. `aws` pins the TLS fingerprint from `deployment.json` and refuses to connect unverified; `local` skips validation (loopback). `EXASOL_DSN` overrides host and port only. Lifecycle: `exasol stop/start -d local`. NEVER `exakit start/stop` (that targets the AWS `default` deployment); on AWS only deploy and run, never stop, start or resize.
- **UDF DNS on Personal nano 2026.2.0-nano.3:** the UDF sandbox has an empty `/etc/resolv.conf` and `/etc/hosts`, so nothing resolves, not even `localhost`. **Workaround approved by Nico (D21):** the fetch UDF's resolver seam tries the system resolver first and falls back to DNS over HTTPS (`https://1.1.1.1/dns-query`, JSON, A records) only on `gaierror`. Only name lookup changes; TLS still verifies the real hostname. Verified 2026-10-21: `/info` returned 200 from a UDF. Keep the fallback configurable and remove it once nano fixes the sandbox.
- No Rust in v1 (D16). Personal ships a builtin RUST SLC; a Rust engine port is backlog only.
- **Python engine environment (D19):** the builtin SLC is Python 3.12.3 + numpy 1.26.4. Pin host test venvs to numpy 1.26.4 (spikes use `spikes/.venv`), since `Generator` streams are not guaranteed across numpy versions. Recommended `sims_per_batch` 1,000–10,000 (at least 2 batches per slot), stored default 10,000, and it is part of the run's reproducibility key.
- **UDF concurrency on Personal = `nrOfCores` per node** (`GROUP BY batch_id`), not the host CPUs. Personal auto-sizes `nrOfCores` and DB RAM at each start from the free host memory (seen: 12 cores / 11.4 GiB, 6 / 5.5, 8 / 7.6). Before benchmarking, check `EXA_SYSTEM_EVENTS` (`DB_RAM_SIZE`) and the `podman logs` sizing lines, and record the sizing with the result.
- `os.getpid()` is 1 in every UDF instance (separate PID namespaces): identify instances with `exa.meta.vm_id`.
- Exasol's string-to-DOUBLE parse (e.g. CSV IMPORT, `CAST('-0.6' AS DOUBLE)`) is not correctly rounded (1 ulp off). Pass model values to UDFs as fixed-scale DECIMAL, and compare host results against values read back from the DB.
